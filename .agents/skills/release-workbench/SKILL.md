# Release Workbench

Treat a release as a transaction. GitHub Actions owns publication; this skill
prepares, approves, dispatches, resumes, and verifies it.

## 1. Establish state

Require exactly one level: `patch`, `minor`, or `major`.

Fetch `origin`, then require:

- the current branch is `main`;
- the working tree is clean;
- local `main` equals `origin/main`;
- GitHub CLI is authenticated for the repository.

Read the current Feature version. If its remote `vX.Y.Z` tag exists, use that
tag's commit as the expected SHA; otherwise use HEAD. Run
`scripts/release-state.sh VERSION EXPECTED_SHA`. A conflict stops for
diagnosis. An incomplete release resumes from the state reported by the
script. A completed current release continues to preparation even when later
infrastructure commits exist on `main`.

This step is complete when the repository is synchronized and the run is
classified as either a new release or one resumable release.

## 2. Prepare a new release

Skip this step when resuming an existing release commit.

Run `scripts/update.sh LEVEL` and stop when it reports `Already current`.
Otherwise run `scripts/update.sh LEVEL --apply`.

The level controls dependency eligibility:

- `patch` keeps tools within their current minor versions;
- `minor` keeps tools within their current major versions;
- `major` permits stable tool major versions.

Patch and minor dependency releases bump the Workbench patch version. Major
dependency releases bump the Workbench minor version. Workbench major releases
are outside this skill.

Run `test/run.sh`, then run the repository's canonical Feature test:

```bash
npx --yes @devcontainers/cli@0.87.0 features test \
  --project-folder . \
  -f workbench \
  --skip-autogenerated \
  --skip-duplicated
```

Generate notes from the latest `v*` tag to the worktree:

```bash
.agents/skills/release-workbench/scripts/release-notes.sh \
  "$(git describe --tags --match 'v*' --abbrev=0)" \
  WORKTREE
```

Show the exact diff, generated notes, version, and proposed commit:

```text
chore(workbench): release vX.Y.Z
```

Ask once for release approval. This step is complete only after the user
approves those exact release contents.

## 3. Commit and pass CI

Stage only:

- `src/workbench/versions.env`
- `src/workbench/checksums.env`
- `src/workbench/devcontainer-feature.json`

Commit with the approved subject and push `main`. Find the push-triggered
`test.yaml` run for that exact commit and wait for it with
`gh run watch --exit-status`.

This step is complete when push CI is green for the release commit.

## 4. Publish or resume

For a new release, dispatch:

```bash
gh workflow run release.yaml \
  --ref main \
  -f expected_version=X.Y.Z \
  -f expected_sha=RELEASE_COMMIT
```

Find the workflow-dispatch run for the exact commit and watch it to completion.
When an earlier run is still active, watch it. When it failed without a state
conflict, rerun only its failed jobs and watch the rerun. The separate Publish
and Release jobs make a post-publication retry safe.

This step is complete when the release workflow succeeds.

## 5. Verify completion

Run `scripts/release-state.sh VERSION RELEASE_COMMIT`. Require:

- classification is `complete`;
- `vX.Y.Z` points to the release commit;
- the GitHub Release exists;
- exact, minor, and major GHCR aliases share the exact digest;
- the repository is clean and synchronized.

Report the workflow, Release, package version, aliases, and commit. Downstream
consumer lockfile updates are a separate task.
